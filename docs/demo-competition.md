# Demo Competition — Top Members / Top Brands (SIMULATION ONLY)

The Demo Competition is a public demo leaderboard: 21 Demo Members and 20 Demo Brands with
simulated sales and earnings. Every figure is generated by a deterministic server-side engine.
**Nothing in it is a real order, commission, payout, wallet, reward or affiliate.** Every public
surface shows one discreet simulation disclosure (see §6).

## 1. Data (migration `20261113_demo_competition`, additive)

| Table | Content |
|---|---|
| `demo_comp_members` | 21 non-archived max. Name, photo, active, `archivedAt`, personal stream (min/max daily orders, price, allocation), network stream (affiliate count, min/max, price, allocation; **no default rate**: off until both are set), generation cursors |
| `demo_comp_member_versions` | Append-only settings snapshots (`effectiveFrom`, `createdBy`) |
| `demo_comp_brands` | 20 non-archived max. Name, image, owner member (FK RESTRICT), `archivedAt`, min/max, price, allocation (default 70 %) |
| `demo_comp_brand_versions` | Append-only settings snapshots |
| `demo_comp_daily_plans` | One immutable plan per stream, profile and Casablanca day: the target order count within the snapshot's min/max |
| `demo_comp_events` | Append-only sale events (1–3 orders each) with price, allocation and earnings snapshots and a unique idempotency key `<stream>:<profile>:<day>:<seq>` |
| `demo_comp_engine` | Single row: enabled (ships **off**), `resumedAt` / `pausedAt` (last switched ON / OFF), defaults (300 DH, 30 %, 70 %), last run |

Database guards:
- CHECK constraints enforce ranges, `earningsCents = round(q × price × bps / 10000)`, stream/owner consistency, and "archived ⇒ disabled".
- **Allocations:** member and brand allocations are separate demo sales streams. Each is validated on its own (0.01 %–100 %); there is no combined 100 % cap, for the defaults or per profile.
- Triggers refuse UPDATE or DELETE of events, plans and versions. Only a cascade from a deleted profile may delete them. The application never deletes a profile (see Archive); the cascade stays possible only for a later, approved cleanup.

## 2. Engine

The engine is in `src/lib/demoCompetition/engine.js` (pure) and `src/lib/services/demoCompetitionService.js`.

- **Calendar:** Africa/Casablanca days, including the 23/25-hour days around Ramadan.
- **Daily target:** each day's target comes from a seeded PRNG (FNV + mulberry32) and is spread over busy-hour weights.
- **Snapshots:** an event uses the settings version in force at its scheduled time. A settings change never rewrites history.
- **Idempotent and concurrency-safe:**
  - per-profile `pg_advisory_xact_lock`;
  - `createMany({ skipDuplicates })` on the unique key;
  - verified with 4 concurrent OS processes in `scripts/demoCompetition.harness.mjs`.
- **Backfill:** every new profile (Initialize or "create") gets its 30-day history immediately, with the same engine, whether the engine is ON or OFF:
  - engine never switched ON yet (initial setup): history up to now;
  - engine OFF after having run: history only up to the moment it was switched OFF.
- **Engine OFF:** nothing is generated while the engine is OFF (worker, read-path catch-up and "Run now", which answers 409 `ENGINE_DISABLED`). When it is switched back ON, generation resumes from that moment (`resumedAt`). The OFF period is never generated afterwards: no catch-up.
- **Archive (instead of delete):** archiving a profile disables it and appends an `active=false` settings version, so nothing is generated after that moment. It leaves the public rankings and the 21 / 20 limits, and keeps its whole history, still readable in the admin.
  - A member that still owns non-archived brands cannot be archived.
  - An archived profile cannot be edited.
  - Restore brings it back **disabled**, within the limits; a brand also needs a non-archived owner. Re-enabling it in the editor resumes generation from that moment.
- **Windows:** statistics use rolling windows of exactly 24 h, 168 h and 720 h, plus all-time. Ranking uses rolling 30-day (720 h) personal earnings only. There is no monthly cycle.
- **Scheduling:**
  - pm2 worker `demo-leaderboard-engine` (`scripts/demo-leaderboard-engine.mjs`, advisory lock `DCMP`, never scale);
  - a throttled catch-up on public reads (≤ every 5 s);
  - "Run now" in the admin.

## 3. Surfaces

- **Admin:** sidebar → Demo Competition: Demo Members, Demo Brands, Live Engine, Homepage Settings. API under `/api/admin/demo-competition/*`, `withAdminAuth`. Profiles are archived and restored (`POST …/{id}/archive`, `POST …/{id}/restore`); there is no DELETE route.
- **Homepage layout (conflict-safe):**
  - The Homepage Builder and Demo Competition → Homepage Settings both save through `PUT /api/admin/homepage-layout` with the revision they loaded (`src/lib/services/homepageLayoutService.js`). If the layout changed in between, the save is refused with 409 `LAYOUT_CONFLICT` and the page reloads; nothing is overwritten silently.
  - The generic `POST /api/setting?type=homepage_layout` is refused (reserved type).
  - The public homepage still reads `GET /api/setting?type=homepage_layout`.
- **Public pages:** `/top-members`, `/top-members/[id]`, `/top-brands`, `/top-brands/[id]`, reading the read-only API `/api/demo-competition/*`. These routes are in the Landing Page Only Mode allowlist.
- **Homepage builder:** independent sections `top_members` and `top_brands`.
- **Affiliate dashboard:**
  - The overview leaderboard (`CompetitionTab` in `src/app/affiliate/dashboard/page.jsx`) now reads `/api/demo-competition/members`. A row opens `/top-members/[id]`, and the cycle / days-left banner is gone.
  - It follows the **dashboard** language (`DASHBOARD_LANG`, French on this branch), never a storefront language chosen elsewhere.
  - When the dashboard localization (Task 7) is merged, pass its language to `CompetitionTab`. Task 7 also edits the old `CompetitionTab` texts, so expect a merge conflict there: keep this branch's component.

## 4. The old demo system (still running, not deleted)

The old system stays in place, untouched. Two consumers still use it, by decision:

| Part | Files |
|---|---|
| Models | `DemoAffiliate`, `DemoAvatar`, `DemoStats`, `DemoEarningsHistory`, `DemoCompetition`, `DemoSettings` (schema.prisma) |
| Service | `src/lib/services/demoService.js` |
| Public API | `src/app/api/demo/leaderboard/route.js`, `src/app/api/demo/affiliate/[id]/route.js` |
| Admin API / UI | `src/app/api/admin/demo/` (route, simulate, reset, avatars), Demo panel in `src/app/admin/affiliates/page.jsx` |
| Worker | `scripts/demo-competition-engine.mjs` (pm2 `demo-competition-engine`) |
| Consumers still on it | `/tsajlim3ana` (`RecruitmentLanding.jsx` → `/api/demo/leaderboard`), Live Activity (`liveActivityEngine.js` → `getDemoIdentityPool`) |
| Tests | `scripts/demoIsolation.test.mjs` |

The two systems never write each other's tables. The new engine writes only `demo_comp_*`; the old one
writes only its own tables. Their pm2 worker names, scripts and advisory locks are all different.

### Retirement, later and only with separate approval

1. Move `/tsajlim3ana` and Live Activity to the new data (a separate decision; not done here).
2. Once nothing reads `/api/demo/*`, stop and remove the `demo-competition-engine` pm2 app.
3. Then remove the old routes, the service, the admin panel and `demoIsolation.test.mjs`.
4. Last, drop the old tables in a separate, reviewed migration, after a backup.

## 5. Operations (not executed by the implementation)

These steps are not done yet. Each one needs explicit approval.

- **Apply migration `20261113_demo_competition`** with `prisma migrate deploy`. The migration is additive and safe to re-run. It only references its own `demo_comp_*` tables and is ordered after `20261112`.
- **Start the worker:**
  ```
  pm2 start ecosystem.config.js --only demo-leaderboard-engine && pm2 save
  ```
- **In the admin, Live Engine:**
  1. Initialize, which creates the profiles, each with its 30-day history. The engine can stay OFF.
  2. Turn the engine on. Live generation starts from that moment.
  3. Edit the profiles: names, photos, rates, and the network rate if wanted.
- **Homepage:** add the sections in the Homepage Builder, or in Demo Competition → Homepage Settings.

## 6. Public wording and the simulation disclosure
The public texts (FR / AR, `src/lib/demoCompetition/i18n.js`) are neutral: no "démo", "test", "bêta" or similar
labels on the affiliate dashboard block, `/top-members`, `/top-brands` or the profiles, and no per-card or header
badge. While the data is simulated, ONE discreet footnote tells visitors so.

- **Single source:** `src/lib/demoCompetition/disclosure.js` — `SIMULATION_DISCLOSURE = { enabled, text: { fr, ar } }`.
  - FR: « Classement basé sur des données simulées : il ne s'agit ni de ventes ni de gains réels. »
  - AR: « ترتيب مبني على بيانات محاكاة: ليست مبيعات ولا أرباحاً حقيقية. »
- **Where it shows:** `<SimulationNote>` (`src/components/demoCompetition/Badges.jsx`, small muted text with
  `role="note"`, page direction) — once at the bottom of every full page / profile (`PageShell`, also on the
  loading, error and not-found states) and once under the dashboard block (`DemoCompetitionBlock`). The page
  metadata (`demoPageMetadata()` in the same module) uses neutral titles and appends the FR sentence to the description.
- **Change the wording:** edit `text.fr` / `text.ar` in `disclosure.js` only (the sentences must not be copied
  anywhere else — `scripts/demoCompetitionPublic.test.mjs` checks it).
- **Disable it** (only once the leaderboards no longer show simulated data): set `enabled: false`. `<SimulationNote>`
  then renders nothing and the descriptions drop the sentence; nothing else changes.

`src/lib/neutralWording.js` (switch `NEUTRAL_WORDING_PREVIEW`) no longer touches these texts; it only holds the
temporary neutral-wording preview of the active "Create Your Own Brand" dashboard (`scripts/neutralWording.test.mjs`).
